Architecture and cryptography

How a vote stays secret
and the count stays honest

Glass Ballot combines four building blocks: Paillier homomorphic encryption, zero-knowledge proofs, RSA signatures and a hash-chained bulletin board. The decryption key is split among several trustees. This page walks through each block with animations, toy numbers you can play with, and real values from the election running on this server.

1The big picture

Six roles, one public bulletin board. Press Play to watch an election from start to finish, or pick a phase. secret data never leaves its owner (except shares and codes handed out once). public data goes on the board for anyone to check.

    Voter deviceKnows: its own RSA private key, its vote, the ballot randomness rᵢ.Never sends any of these.
    ServerSees: encrypted ballots, public keys, proofs.Cannot decrypt (holds no key share), cannot forge a voter signature, cannot change the board unnoticed.
    TrusteesEach knows one share sⱼ of the decryption exponent.Need all k shares together. They only ever decrypt the published totals.
    AnyoneCan download the board and re-check every signature, proof, hash and the final count.

    3Paillier encryption: adding votes without opening them

    Key generation picks two large primes p, q and publishes n = p·q (2048 bits) with g = n + 1. To encrypt a message m with fresh randomness r:

    c = gᵐ · rⁿ mod n² = (1 + m·n) · rⁿ mod n²

    The rⁿ factor hides m completely, so encrypting the same vote twice gives unrelated ciphertexts. The key property is that multiplying ciphertexts adds the plaintexts:

    Enc(m₁, r₁) · Enc(m₂, r₂) = Enc(m₁ + m₂, r₁·r₂)

    So the server multiplies every ballot's ciphertext for a candidate and gets an encryption of that candidate's total, without opening a single ballot.

    Try it with toy numbersp = 7, q = 11, so n = 77, n² = 5929

        4The ballot: one-hot encryption plus zero-knowledge proofs

        A vote for candidate j out of k becomes a one-hot vector with a 1 at position j and 0 everywhere else. Each entry is encrypted separately. Encryption alone would let a cheater encrypt a 5 or a −3, so the browser attaches proofs that convince the server without revealing the vote:

        Vote for:

        0-or-1 proof, one per candidate

        An OR-proof (Cramer–Damgård–Schoenmakers). Statement: "c encrypts 0 or c encrypts 1". Equivalently, c or c·g⁻¹ is an n-th power. The prover runs the real Σ-protocol on the true branch and simulates the false one by picking its challenge first. The verifier checks e₀ + e₁ = H(…) and zⱼⁿ = aⱼ·uⱼ^eⱼ for both branches. Both look identical, so it cannot tell which was real.

        Sum proof, one per ballot

        The product of all of the ballot's ciphertexts must encrypt exactly 1. With R = Π rᵢ, this means (Π cᵢ)·g⁻¹ = Rⁿ. The voter proves knowledge of that n-th root R. This stops "1 for Alice and 1 for Bob".

        Fiat–Shamir with context

        The verifier's random challenge is replaced by e = SHA-256(domain, n, election id, credential id, candidate, commitments) truncated to 128 bits. Because the credential id is inside the hash, copying someone else's ballot under your credential makes every proof fail.

        5Credentials and signatures: who may vote, and once
        
        
        
          
        
            
          
              
        1. Device key. The voter's browser generates a 2048-bit RSA key pair (n, e = 65537, d). The private exponent d never leaves the device.
          2. 
              
        2. Registration. The device sends its public key with a one-time code. The authority signs
                {election_id, credential_id = SHA-256(public key), voter_public_key}, and that credential goes on the board.
          3. 
              
        3. Voting. The ballot body is signed with d. The server, and later anyone, checks the signature against the credential on the board.
                One credential means one ballot (enforced by the service, a unique database index and the verifier).
          4. 
            
        
            
        The scheme is RSASSA-PKCS1-v1_5 with SHA-256 (RFC 8017), written from scratch in Python (crypto/rsa.py) and JS (static/gbcrypto.js).
              Signing uses the CRT and checks its own result.

        6The bulletin board: a hash chain
        
        
        Every entry stores the SHA-256 hash of the entry before it: entry_hash = SHA-256(seq, kind, payload, prev_hash).
          Editing anything changes that entry's hash, which no longer matches the next entry's prev_hash, and every later link breaks with it.
          The hashes below are real SHA-256 values, computed in your browser. Edit a block to see the damage spread.
        
        
        
          
        
          
        
            In the database, triggers also refuse UPDATE and DELETE, and unique indexes allow one ballot per credential.
        
        
        
      
        

      
      
        
        
        7Tally and threshold decryption
        
        
        
          
        
            
        After the polls close, the encrypted total for each candidate is T = Π cᵢ = Enc(Σ mᵢ, R) with R = Π rᵢ.
        
            
        Splitting the key. With λ = lcm(p−1, q−1), set e′ = n⁻¹ mod λ.
              Then (T mod n)^e′ = R, so knowing e′ lets you recover the randomness. At the ceremony e′ is split into additive shares
              e′ = s₁ + … + sₖ (mod λ), one per trustee, and p, q, λ and e′ are deleted.
        
            
        Decrypting. Each trustee recomputes T from the board and publishes Pⱼ = (T mod n)^sⱼ mod n.
              Multiplying all the partials gives R. Anyone can then check gᵐ · Rⁿ = T (mod n²) and read off m.
              Since x ↦ xⁿ is one-to-one on ℤₙ*, only the true R and the true m pass this check, so it is a complete, public check.
              Any k−1 trustees together get nothing usable.
        
          
        
          
        
            
        Three trustees, toy keyn = 77, λ = 30, e′ = 77⁻¹ mod 30 = 23

          8Verification and audits
          
        
          
          
          
            
          Universal verifiability. scripts/verify_board.py (and the Verify button) takes only the board and re-checks everything.
              Here is each check and the attack it catches:
          
            
            
          
            
          
            
            
            Individual verifiability.
            
            
              
              
            • Recorded as cast: your receipt is SHA-256 of your signed ballot. Your device computes it too, and you can find it on the board.
              • 
              
            • Cast as intended (Benaloh challenge): the device seals the ballot and commits to its fingerprint before you choose to cast or audit.
                An audit reveals every rᵢ, and both the browser and the server's independent Python code re-encrypt your claimed choice. A device that cheats
                cannot tell whether a ballot will be audited, so it gets caught with high probability over repeated audits.
              • 
              
            • Same board for everyone: the head hash is shown in the app. Compare it with other observers to detect a server showing different people different boards.
              •

            9Security goals and how each one is met
            
        
            
          
            
            
            GoalMechanismEnforced in
            
            
              
            Confidentiality (ballot secrecy)Paillier encryption in the voter's browser. The server never sees a vote. Only totals are ever decrypted, and decrypting them needs all k trustees.static/gbcrypto.js, election/tally.py
            
              
            IntegrityHash-chained append-only board, plus database triggers and unique indexes, plus a public verifier that recomputes everything.bulletin_board.py, sqlite_board.py, verifier.py
            
              
            Authentication / eligibilityOne-time registration codes (only their hashes are stored). Each credential is signed by the authority and bound to a device key. Each ballot is signed by that device.authority.py, web/server.py
            
              
            One voter, one voteThe service checks, a unique index in SQLite enforces it, and the verifier re-checks it.service.py, sqlite_board.py, verifier.py
            
              
            Ballot validityZero-knowledge 0-or-1 OR-proofs and a sum proof, bound to the election and credential with Fiat–Shamir.crypto/sigma.py, crypto/proofs.py
            
              
            Non-repudiation / accountabilitySigned credentials and ballots, and per-trustee partials, all public on the board.crypto/rsa.py
            
              
            Universal verifiabilityAnyone can run verify_board.py on the board file. No keys and no trust in the server are needed.scripts/verify_board.py
            
              
            Individual verifiabilityReceipts (recorded as cast) and the Benaloh audit (cast as intended).static/app.js, /api/audit
            
              
            AvailabilityProofs are checked in a process pool outside the lock. POSTs are rate-limited per IP, request bodies are capped, and the board is read incrementally.web/server.py
            
              
            Transport securityOptional HTTPS (--tls), a strict Content-Security-Policy, nosniff, frame-deny, and no referrer.scripts/serve.py, web/server.py
            
                        
          
            
        
            
        
            
          
            Honest limits (what a reviewer should ask about)
            
          
              
            
            • Coercion resistance is out of scope. As in Helios, a voter could prove how they voted by revealing the ballot randomness. Real coercion resistance needs a different protocol (JCJ/Civitas: anonymous credentials, fake credentials and mixnets).
              • 
            
            • Trusted dealer. One process generates the key and splits it, then deletes it. Distributed generation of a Paillier modulus is possible (Boneh–Franklin style) but much more complex.
              • 
            
            • k-of-k shares. Every trustee is needed, so one missing trustee delays the result. t-of-k Shamir sharing (Shoup / Damgård–Jurik) would tolerate absences, but needs safe primes.
              • 
            
            • Demo convenience. In the demo one browser plays every role, so all the secrets sit in one localStorage. In real use each role is a separate device.
              • 
          
            
        
            
      
            

      
      
            
        
            10Where the code lives
            
        
            
          
            
            
              
            glassballot/crypto/Number theory, Paillier, RSA, canonical JSON + SHA-256, Fiat–Shamir, Σ-protocols and proofs. Knows nothing about elections.
            
              
            glassballot/election/Parameters, authority (credentials), ballot, bulletin board (JSONL and SQLite), service (accept or reject), tally (threshold decryption), verifier.
            
              
            glassballot/web/server.pyStdlib HTTP API: roles, tokens, process pool, rate limiting, security headers, TLS.
            
              
            glassballot/web/static/gbcrypto.jsThe browser half: a line-by-line port of the Python crypto, checked against it by tests/test_js_crypto.py.
            
              
            glassballot/web/static/worker.jsWeb Worker: key generation, encryption, proofs, signing and trustee partials run off the main thread.
            
              
            scripts/serve.py (web app), run_demo.py (CLI election), verify_board.py (public verifier), attack_demo.py, load_test.py.
            
              
            tests/Unit tests (crypto, election, threshold, SQLite), HTTP API test, JS↔Python cross-checks, and the headless-Chrome end-to-end flow.
